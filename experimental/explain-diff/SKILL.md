# explain-diff

## 왜 쓰나

에이전트가 코드를 쓰면서 코드를 만드는 비용은 거의 사라졌습니다. 이제 병목은 "무엇이 바뀌었나"를 사람이 이해하는 일입니다. 이해하지 못하면 두 가지 문제가 생깁니다.

- **인지 부채**: 내 영역인데, 나중에 디버깅하거나 다음 기능을 설계할 때 코드를 설명하지 못합니다.
- **모르는 변경**: 남의 영역을 바꿨는데 담당자가 모릅니다. 담당자는 나중에 놀라거나, 그 변경 때문에 문제를 겪습니다.

둘 다 "무엇이 바뀌었나"에 답하는 일이고, 다른 것은 읽는 사람뿐입니다.

이 스킬은 안전장치가 아닙니다. 변경이 맞는지 판정하거나 머지를 허락하지 않습니다. 목적은 사람이 변경을 설명할 수 있는 상태로 만드는 것입니다.

이 스킬이 새 병목이 되면 안 됩니다. 모든 변경에 긴 문서를 만들면, 읽고 기억하는 일이 새 병목이 됩니다. 그래서 세 가지를 지킵니다.

- 사람이 이미 아는 것은 다시 설명하지 않습니다. 내가 읽을 때는 점검을 먼저 하고, 막힌 곳만 설명합니다.
- 분량은 변경 크기에 맞춥니다.
- 오래 남길 이해는 문서로 쌓아 두지 않습니다. 그 영역의 현재 상태 문서(README 등)가 틀리게 됐을 때만 고칩니다.

## 무엇을 쓰나

좋은 설명은 다섯 가지를 만족합니다. 모든 판단은 이 기준을 따릅니다.

1. **파일 단위가 아니라 흐름 단위로 씁니다.** 사용자 흐름이나 데이터 흐름이 이전에 어땠고 이후에 어떤지를 씁니다.
2. **시나리오에 드러나지 않는 변경을 꺼냅니다.** 아래와 같은 변경은 화면에 보이지 않지만, 놓치면 사고로 이어집니다.
   - 데이터 구조
   - 권한
   - 설정과 환경 변수
   - 외부 계약 (응답 형식, 공개 API)
   - 예약 작업이나 배치
   - 여러 곳이 함께 쓰는 코드
   - 영역 사이에 새로 생긴 의존

   이런 변경을 찾으면 그것을 쓰는 곳까지 diff 밖에서 찾습니다. 가장 큰 위험은 diff 밖에 있는 경우가 많습니다. 확신이 없으면 빼지 말고 "확인 필요"로 넣습니다.
3. **모든 설명에 근거를 붙입니다.**
   - 근거는 저장소 루트 기준 경로와 줄로 씁니다. 예: `services/payment/checkout.ts:11`
   - 현재 브랜치에 없는 줄, 곧 지워진 줄은 앞에 브랜치를 붙입니다. 예: `main:services/payment/checkout.ts:10`
   - 실행해서 확인할 수 있으면 실행합니다. 저장소를 바꾸지 않도록 임시 디렉터리를 씁니다.
4. **의도를 지어내지 않습니다.** 의도는 "왜 바꿨나"입니다. "무엇을 바꿨나"와 다릅니다. 커밋 메시지, 연결된 handoff 문서, 코드 주석에 이유가 있을 때만 의도로 씁니다. 커밋 메시지에 무엇만 있고 이유가 없으면 "의도 불명"이라고 쓰고, 그 커밋 메시지를 그대로 인용합니다.
5. **짧게, 위험한 순서로 씁니다.** 읽는 사람의 시간도 병목입니다. 같은 내용을 두 번 쓰지 않습니다.

문장의 차이는 이렇습니다.

| 나쁜 예 | 좋은 예 | 이유 |
|---|---|---|
| `checkout.ts`를 수정했습니다 | 결제가 실패해도 입력한 배송지가 남습니다 (`services/payment/checkout.ts:11`. 전에는 지웠습니다, `main:services/payment/checkout.ts:10`) | 흐름 단위이고 근거가 있음 |
| 마이그레이션을 추가했습니다 | `orders`에 열을 추가했습니다. 이 테이블을 `SELECT *`로 내보내는 배치가 있어서 내보내는 파일에 열이 하나 늘어납니다 (`jobs/settle.ts:2`) | 쓰는 곳까지 찾음 |
| 재시도 로직이 개선되었습니다 | 의도 불명. 커밋 메시지에 이유가 없습니다 | 지어내지 않음 |

이 예시는 문장의 질을 보여 주려는 것입니다. 특정 저장소의 규칙이 아닙니다.

## 분량

| diff 크기 | 요약 | 깊은 설명 (막힌 곳만) | 퀴즈 |
|---|---|---|---|
| 작음 (바뀐 줄 50줄 미만) | 15줄 이내 | 막힌 질문 하나당 10줄 이내 | 막힌 질문 수만큼 |
| 중간 (50~500줄) | 30줄 이내 | 막힌 질문 하나당 20줄 이내 | 3문항 이내 |
| 큼 (500줄 이상) | 30줄 이내. 시나리오를 묶고 나머지는 "그 밖에 n개" | 막힌 질문 하나당 30줄 이내 | 3문항 이내 |

- 줄 수는 제목과 범위 같은 머리 줄을 빼고, 시나리오와 설명만 셉니다.
- 넘치면 시나리오와 설명을 줄입니다. 덜 중요한 시나리오는 "그 밖에 n개"로 묶습니다.
- "시나리오에 드러나지 않는 변경"은 분량 때문에 빼지 않습니다. 이 스킬이 막으려는 사고가 바로 여기서 생기기 때문입니다. 항목이 많으면 항목마다 한 줄로 줄입니다.

## 절차

### 1. 범위 정하기

- 인자로 받은 커밋, 브랜치, PR을 씁니다.
- 받지 않았으면 현재 브랜치와 기본 브랜치의 차이를 씁니다.
  - 기본 브랜치는 `git symbolic-ref --short refs/remotes/origin/HEAD`로 찾습니다. 실패하면 `main`, `master` 순서로 확인합니다.
  - 범위는 `git diff <기본 브랜치>...HEAD`입니다.
- 커밋하지 않은 변경은 범위에 넣지 않습니다. 있으면 그런 변경이 있다고 한 줄로만 알립니다. 사용자가 넣으라고 하면 넣습니다.
- git 저장소가 아니면 diff를 달라고 합니다.

### 2. 사용자가 요청한 일 하나만 합니다

요청이 아래 둘 중 어느 쪽인지 정합니다. 모르면 한 번 묻습니다.

- **변경 노트**: 다른 담당자에게 알릴 내용을 만듭니다. 3-a로 갑니다.
- **이해 점검**: 내가 이 변경을 설명할 수 있는지 확인합니다. 3-b로 갑니다.

요청하지 않은 일은 하지 않습니다. 다만 필요해 보이면 끝에 한 줄로 제안합니다.

- 변경 노트를 쓰다가 내 영역의 변경이 보였을 때: "내 영역의 변경도 있습니다. 이해 점검이 필요하면 말씀해 주세요."
- 이해 점검을 하다가 남의 영역 변경이 보였을 때: "다른 담당자의 영역도 바뀌었습니다. 변경 노트가 필요하면 말씀해 주세요." 누구 영역인지 모르면 "다른 사람이 담당하는 파일이 있다면 변경 노트를 만들 수 있습니다"라고 씁니다.

어느 파일이 누구 담당인지는 사용자가 말해 주거나, CODEOWNERS나 CLAUDE.md에 적혀 있을 때만 판단합니다. 변경 노트를 쓰는데 그 정보가 없으면 묻습니다. 커밋 기록으로 추측하지 않습니다.

이름 바꾸기, 포맷, 주석, 의존성 버전, lockfile, 자동 생성된 코드는 기계적 변경으로 보고, 어디서든 "기타"에 한 줄로 묶습니다. 변경이 전부 기계적 변경이면 "설명할 변경 없음"이라고 말하고 끝냅니다.

### 3-a. 변경 노트

1. 그 담당자의 영역에 닿는 변경만 골라 형식 A로 씁니다. 변경을 쓰는 곳은 영역에 상관없이 찾습니다.
2. "시나리오에 드러나지 않는 변경"의 항목마다 그 담당자에게 물을 확인 질문을 같은 줄 끝에 붙입니다. 그 담당자만 답할 수 있고, 예, 아니요로 답할 수 있는 질문으로 씁니다. 항목과 상관없는 질문만 "열린 질문"에 씁니다.
3. 이 변경 때문에 그 영역의 README 같은 현재 상태 문서의 설명이 틀리게 됐으면 "현재 상태 문서"에 적습니다. 남의 영역 문서는 고치지 않습니다.
4. 대화에 보여 주고 끝냅니다. 어디로 보낼지는 사용자가 정합니다. 저장하거나 보내자고 먼저 묻지 않습니다.

### 3-b. 이해 점검

순서가 중요합니다. 요약을 먼저 보여 주면 점검이 의미가 없어집니다.

1. **diff를 읽고 요약을 머릿속에만 준비합니다.** 아직 사용자에게 보여 주지 않습니다.
2. **세 질문을 한 번에 묻고 답을 기다립니다.** 코드를 보지 말고 짧게 답해 달라고 합니다. 점검 대상은 이번 범위의 변경 전체입니다.
   1. 이 변경은 왜 필요했나?
   2. 어떤 흐름이 어떻게 바뀌었나?
   3. 이게 망가지면 어디부터 봐야 하나?
3. **답이 없거나 사용자가 건너뛰면** 형식 A의 요약만 보여 주고 5단계로 갑니다.
4. **질문마다 판정합니다.** 판정은 셋 가운데 하나입니다.
   - **맞음**: 요약과 일치합니다.
   - **빠짐**: 요약의 핵심이 답에 없습니다.
   - **다름**: 요약과 어긋납니다.

   질문별 기준은 이렇습니다.
   - **왜**: 답이 이 변경이 실제로 하는 일과 맞는지 봅니다. 의도가 "의도 불명"이면 판정 옆에 "근거 약함"을 붙입니다. 이유를 확인할 기록이 없다는 뜻입니다.
   - **흐름**: 이전과 이후의 핵심 흐름, 그리고 위험이 가장 큰 안 보이는 변경 하나가 답에 있는지 봅니다.
   - **망가지면**: 동작을 실제로 정하는 지점까지 말했는지 봅니다. 조건, 설정, 데이터가 그런 지점입니다. 시작점만 말했으면 "빠짐"입니다.

   한 답에 맞는 부분과 빠진 부분이 함께 있으면 "빠짐"으로 판정합니다. 이 점검의 목적은 빈틈을 찾는 것입니다. 화면 표시처럼 저장소로 확인할 수 없는 부분은 판정에서 빼고 "확인 불가"라고 덧붙입니다.
5. **결과를 보여 줍니다.**
   - 판정 세 줄을 보여 줍니다. 판정마다 빠지거나 다른 내용을 근거와 함께 한 줄로 씁니다.
   - 셋 다 맞음이면 "이 변경을 설명할 수 있는 상태입니다"라고 말합니다. 요약은 보여 주지 않습니다. 이미 아는 내용이기 때문입니다.
   - 빠짐이나 다름이 있으면 막힌 질문에 대해서만 형식 B로 설명합니다.
6. **퀴즈를 냅니다.** 막힌 부분에 대해서만 냅니다. 사용자가 답한 뒤에 답을 보여 줍니다. 틀린 문항은 근거와 함께 한두 줄로 다시 짚습니다. 다시 점검하지는 않습니다. 사용자가 원하면 건너뜁니다.

### 4. 현재 상태 문서

아래 경우에만 그 영역의 README 같은 문서를 고치자고 제안합니다. 1~3줄을 diff 형태로 보여 줍니다.

- 문서에 적힌 설명이 이번 변경으로 틀리게 됐을 때
- 다른 사람이 알아야 하는 새 개념이나 새 모듈이 생겼을 때

함수 하나가 바뀐 정도로는 제안하지 않습니다.

- 내 영역의 문서이면 고칠 내용을 diff로 보여 주고, 사용자가 승인한 뒤에 고칩니다.
- 남의 영역의 문서이면 고치지 않고, 3-a의 노트에만 적습니다.
- 누구 영역인지 모르면 diff를 만들지 않습니다. 어느 문서의 몇째 줄이 틀리게 됐는지만 한 줄로 알립니다. 담당을 묻는 질문을 따로 하지 않습니다.

### 5. 마무리

- 결과는 대화에 보여 주는 것으로 끝냅니다. 사용자가 요청할 때만 파일로 저장합니다.
- explain diff를 모아 두는 폴더를 만들자고 제안하지 않습니다.

## 형식 A: 요약

```markdown
## 무엇이 바뀌었나: [제목]
범위: [기본 브랜치...작업 브랜치 @ 커밋]
읽는 사람: [나, 또는 담당자]
의도: [커밋 메시지나 연결 문서의 이유. 없으면 "의도 불명"]

### 시나리오
- [이름]: [상황]
  - 이전: [동작] (근거)
  - 이후: [동작] (근거)

### 시나리오에 드러나지 않는 변경 (위험한 순서)
1. [종류]: [내용]. 쓰는 곳: [diff 밖 포함] (근거) [확인 필요] → 확인: [변경 노트일 때만. 담당자에게 물을 질문]

### 열린 질문
1. [위 항목과 상관없는 질문만]

### 현재 상태 문서
- [틀리게 된 문서와 줄. 없으면 이 절을 뺍니다]

### 기타
- [기계적 변경 한 줄. 없으면 이 절을 뺍니다]
```

## 형식 B: 깊은 설명 (막힌 질문마다)

- **이전과 이후**: 막힌 부분의 동작이 어떻게 바뀌었는지 씁니다.
- **핵심 코드**: 그 동작을 정하는 코드 몇 줄과, 그 앞에 붙이는 한두 줄 설명입니다.
- **망가지면 볼 곳**: "망가지면" 질문에서 막혔을 때만 씁니다.

분량은 "분량" 표를 따릅니다.

## 문장 규칙

- 한국어로 짧게 씁니다. 한 문장에는 생각 하나만 담습니다.
- 파일, 함수, 설정은 실제 이름으로 씁니다.
- "~를 통해", "~를 진행합니다" 같은 번역투를 쓰지 않습니다.

## 하지 말 것

- 의도를 지어내지 않습니다.
- "머지해도 됩니다"처럼 허락하는 말을 하지 않습니다.
- 에이전트가 쓴 코드인지 판단하지 않습니다. 커밋 정보로는 알 수 없습니다.
- 이해 점검에서 질문보다 요약을 먼저 보여 주지 않습니다.
- 사용자가 요청하지 않은 일을 하지 않습니다.
